C言語で私の好きなゲームのひとつの音ゲーを、プログラムに出会って数ヶ月の時に作ってみたいと思い自分なりに作ってみてるプログラムです。

私は専門学校に進学してほぼ初めてパソコンを触りだして、授業で初めて触った人生初のプログラム言語がC言語でした。
また、当時お家には触れるパソコンがなくプログラムができる環境がC言語しかなかったのですが、とりあえず作ってみたかったのでこの作品はC言語でのプログラムになります。

授業で習った基礎的な関数以外はAIやネットで関数名および軽く使い方を調べましたが、コード自体は自分でこうしたいななどの作りたい内容の想いをノリで書いている作品です。

# プログラムについて
ファイルは大きく分けて3種類あります。
* メインファイル([main.c](https://github.com/houki811/C-rhythm_game/blob/main/rhythm_game/main.c))

  モード選択や楽曲選択等の選択するプログラムと、メインのリズムゲームのプログラムがあります。
* 創作モード用ファイル([rhythm_game_editor.h](https://github.com/houki811/C-rhythm_game/blob/main/rhythm_game/rhythm_game_editor.h))

  譜面を創作することができるプログラムがあります。
* #define用ファイル
  * [rhythm_game.define_file.h](https://github.com/houki811/C-rhythm_game/blob/main/rhythm_game/rhythm_game.define_file.h)

    上記のファイルで使っている定数をまとめているファイルです。
  * [error_code_define.h](https://github.com/houki811/C-rhythm_game/blob/main/rhythm_game/error_code_define.h)

    fopen等で失敗したときのどこで失敗したのかわかりやすくしたくて作ったエラーコードの定数をまとめているファイルです。(いわゆる自分用です)

以上、上記の3種類です。

全体を通して意識したのはできるだけメモリを節約することです。
ノーツを処理する二次元配列では譜面ファイルのデータをすべて代入するのではなく、画面に出ている分だけを保存しておき、今いらない譜面データは保存しないことで節約を心がけています。
また、プログラム全体ではキーが押されたかどうかは重要ですが、ノーツの場所と違いキーの押されている状況はそこまで人間にわかりやすい一次元配列等の変数を使う必要はないと判断し、
char型の8ビット変数の1ビットずつに、押されているなら`1`、押されていないなら`0`で判断するようにして節約を心がけました。

# メインファイルについて

* モード選択のコードについて

  モード等の選択のプログラムはできるだけ私の想定してる文字以外が入力されても誤作動しないように`scanf()`で戻り値を確認し、異常があるなら`getchar()`を使い入力された値を保持しているバッファを、
  空にしています。
  また、リズムゲームにはあると助かり、遊びの幅も広がるノーツの基本速度を変更できるようにし、ノーツの認識力を上げれるようにしたりあえてゆっくりにして難しくしたりなど、
  プレイヤーの遊びの幅が広がるように実装しました。
  それに伴い、BPMはそのままにする必要があるので、早くなればなるほどロングノーツなら続くようにただし、コンボ数が速度によって変動しないようにロングノーツのダミー(`LONG_NOTE_FAKE`等の定数)を、
  それ以外のノーツは空白(`NOT_NOTE`の定数)を、速度によって代入する行を調整して速度によってBPM、コンボ数に影響がないように挑戦してみました。
  設定の状態は保存してくれないとプレイヤー側の負担が大きいと思います。なので保存するようにファイルを使い、ベストスコアが見えるとプレイヤーの満足感や、達成感、目標等が生まれ楽しくなりそうだと思いファイルで保存するようにしたりと、
  今まで私が普通に常識として使い遊んでいたセーブ機能を自分なりに考えて実装してみました。
  楽曲選択に関してはリズムゲームは日々譜面は増えていくのが楽しめるし、拡張性もあります。なので今後譜面が増えたりしても対応できるようにファイルを使ったり`for()`等の使い方を考えて、
  創作モードで新しく作った譜面もコード側を変更しなくてもよいようにしてみました。
  
* リズムゲームのコードについて

  リズムゲームには時間がもっとも重要だと思います。
  なので私がわかる範囲にはなりますが`QueryPerformanceFrequency()`や`QueryPerformanceCounter()`を使いできるだけ正確さを目指してみたり、
  FPSの管理にははある程度の時間をまず`Sleep()`し、そこから1フレームの時間になるまでループを続けることで`Sleep()`関数の大まかな停止よりも正確に近づけられるようにしています。
  画面の表示ですが、1個ずつ`printf()`していくと1つずつ表示される影響で画面がチカチカしてしまってました。
  そこで、AIで調べて`strcat()`で連結して1個の`printf()`で表示するようにし、画面の更新の仕方も`system("cls");`で画面をクリアするのではなく`"\x1b[H"`を使い、画面の最大行の0列目にカーソルを移動して上書きする方法を知り実装してみました。
  キーの入力の関数は最初`_getch()`でしていたのですがロングノーツの長押しや離す反応、同時押しの不安定さに気づき、調べて今の`GetAsyncKeyState()`に変更してプレイヤーの楽しいの気持ちにつながりそうな反応の多様化を目指しました。
  
  私の持論になるのですがリズムゲームはノーツの完成度も結構楽しめるゲームとして大事だと思います。
  私がよく遊んでいる音ゲーでは、例えばロングノーツだけを見てもぐにゃぐにゃしたり幅が変わったりとロングノーツだけでも、
  autoで見ても楽しかったり、飽きにくかったりとバリエーションがあるだけで譜面作るのも遊ぶのも楽しさが増えると思ってます。
  そんな譜面を作れるような使えるようなゲーム作ってみたいなと思い、ノーツの部分はこだわってみました。
  その中でもひとつのノーツでも複数レーンまたぐノーツは考え方が他よりパターンが多くなる分作るのが少し大変でしたが、
  パソコンでのゲームを少しでも派手にしたりプレイヤーが遊ぶのも作るのも楽しめそうなように想像してその想いを私なりに形にしてみました。
  
* ノーツについて
  
  ノーマルノーツでは長押ししてても上のノーツが一緒を反応しない、タップした判定にならないようにするなどを`now_kye_solo = kye_nowtouch & ~kye_oldtouch;`で、今押されているキーかつ前回押されていなかったキーの論理演算して、
  新しくキーが押されて初めて反応するように対策してみました。
  ロングノーツでは開始用のノーツ、終わり用のノーツ、繋げているときのノーツの3種類を用意することでずっと押し続けても反応するように設計できたり、
  ロングノーツの最初はしっかり叩かないとmissするようにしたり、最後はキー離さなくてもいいのか`now_kye_longend = ~kye_nowtouch & kye_oldtouch;`で今押されてないキーかつ前回押されていたキーの論理演算を使って離さないといけないプログラムも作り、パターンをたくさん用意して創作も遊ぶのも自由度がC言語でも広がってくれるように実装しました。
  トレースノーツでは基本ロングノーツと仕組みは同じですが、ロングノーツと違って長押しでも単押しでも通用するノーツである必要があるため、判定をロングノーツより厳しく、でも早く押したとしても押し続けているのならmissにならないので、ノーマルノーツよりもかは緩い判定にしてます。
  
  ノーツを動かしている方法はノーツのデータが入っている二次元配列`char note[ARRAY_GYO][7];`を`tempo_sum = ((double)60 / tempo * (double)1000) / (double)note_speed;`で1拍の時間になったら最大行から1行ずつ下げることでノーツの流れを作っています。
  また、判定は現状はわかりやすい行単位での判定にしています。

  ノーマルノーツの判定処理([main.c](https://github.com/houki811/C-rhythm_game/blob/main/rhythm_game/main.c)の`int solo_note(int hantei, char hit, int notenumber, int notenumber_link)`関数)は、ノーマルノーツだけではなくロングノーツの始まりと終わりのノーツも同じ工程で処理できると思い、
  ノーマルノーツの判定処理に関しては、関数を作り判別したいノーツの定数を引き渡すことで動作するようにして、コードの量を少しでも減らせるように関数を分けました。
  同じ理由でノーツをスルーしてしまったときのmissの判定処理([main.c](https://github.com/houki811/C-rhythm_game/blob/main/rhythm_game/main.c)の`void miss_note(int i, int notenumber, int notenumber_link)`関数)も関数化しています。

* リザルトについて
  
  リザルトはそのゲーム中の最大コンボ数と、判定の結果が表示されます。
  最大コンボ数が更新された、または判定の精度がよくなったときにのみ、[rhythm_game_result.txt](https://github.com/houki811/C-rhythm_game/blob/main/rhythm_game/rhythm_game_result.txt)に保存されるようにしているので、
  FULLCOMBO等をできなくても最大コンボ数を更新できれば楽曲選択時のベストスコアは変動するようにしているので、やりこみ要素のひとつの成績もちょっと更新しやすく、どれぐらいできているのかがわかりやすいわかりやすいかなと思い実装してみました。

# 創作モードについて

  私自身リズムゲームを遊ぶのも十分楽しいですが、その譜面が作れるならもっと楽しめると思いました。
  また、作っているときに気づいたのですが、譜面を私などの開発側的にも効率化につながり、一石二鳥だと気づいて自分なりに実装してみました。
  
* ノーツの入力、機能の選択について
  
  メインのときと同様に想定外の入力がされてもできる限り対処できるようにしてみることは挑戦し、入力もしやすいように考えて作りました。
  最初の選択ではノーツを入れる列を入力するか、編集する行を変更するか、今の行からBPMの変更をするかの選択ができます。
  * ノーツの列指定

    `A S D J K L`のどこにノーツを入力するのかを選択できるようにしました。
  * 編集行の変更

    入力したことある行かつ最新の行から16行までの行に移動できます。
    編集が始まったばかりの時にまだ編集したことない行に移動されるとBPMの同期やデータがおかしくなるので、徐々に編集できる行が増えるように設計しました。
  * BPMの変更
    今の行からBPMを変更できるようにしました。
    メインファイルのリズムゲームのコードの使用上今の行からBPMを変えるには13行先の行にBPMを保存する必要があるため、その使用が正しく動くように、最初は1行目のみから1行ずつ増えていき、
    最大3行目までBPM変更ができるようにしました。
    変更しない行には0を代入することでコードをできるだけわかりやすくして0は現状維持、0以外の値ならBPMがその値になるようにしました。
